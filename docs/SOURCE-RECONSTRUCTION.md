# Source reconstruction — M2 source slice complete

The Rust engine now accepts one explicitly supplied Solidity file, invokes a local `solc --standard-json`, and fills `EconomicFunction` records from the compiler AST. Run it with a `solc` executable installed locally:

```sh
cargo run -p security-engine -- tests/fixtures/VaultWithOracle.sol /path/to/solc
```

The command prints structured JSON IR. The library also exposes `reconstruct_source_file` and `reconstruct_from_ast_json` for callers that already have compiler output.

## Extracted now

- Named vault operations, previews, conversions and oracle price functions, classified from their names with `Inferred` confidence.
- Direct storage reads/writes, including compound assignments and indexed mappings, linked to source byte spans.
- Internal calls to functions in the same contract or a base contract supplied in the file, explicit contract/address external calls, modifiers, arithmetic expressions and branch conditions.
- Oracle-call candidates when a price method is invoked on an oracle/feed/aggregator typed or named receiver.
- `delegatecall` receiver as a tentative proxy implementation candidate when its concrete target is unknown. For an `immutable` state address assigned directly to `address(new LocalContract())` in the constructor, `ProxyRelation` links the assignment, locally declared implementation, and delegatecall with source spans and inferred confidence.
- Modifiers defined in the same file, including inherited modifiers, resolved by the compiler's declaration ID. Their direct storage access, calls, arithmetic, and `require`/`assert` conditions are retained in `AppliedModifier` with invocation and definition spans, and included in the function's dependency lists. Parameters are paired with invocation arguments using source spans. For one `_` per modifier, the control graph runs through modifiers in source order, through the function body, then through modifier postludes in reverse order. A function-body `return` continues through those postludes, as specified by the [Solidity documentation](https://docs.soliditylang.org/en/latest/contracts.html#function-modifiers).
- Internal call paths across same-file inheritance to storage reads/writes, oracle candidates and share/asset conversions. Every hop keeps the call-site span. Recursive paths and excessive depth are truncated with explicit uncertainty. These paths establish syntactic reachability, not value dependence.
- Conservative value tracing through scalar locals, parameters, assignments, returns, internal calls, simple modifier parameter bindings, guards, conversion arguments and storage writes. It distinguishes an oracle used only by a guard from an oracle value passed into `convertToShares`. Source spans and contributing call sites are retained on each `ValueFlow`.
- A structural source control graph with `entry`, `exit`, and AST statement/expression nodes. Edges distinguish sequential flow, true/false branches, loop back edges, and exits. Each edge carries a source span. The extractor handles `if`, `return`, `revert` statements, `require`/`assert` guards, one ternary expression per statement, `while`, `for`, `do while`, `break`, and `continue`. In a `for` loop, `continue` reaches the update before the condition; in `do while`, it reaches the condition. Nested loops keep their own break and continue destinations.

Tests use AST snapshots generated by solc 0.8.37 from eight small fixtures. They verify source locations, vault accounting relations, inherited calls, multi-hop value propagation, modifier effects, control edges, fixed proxy evidence, and tentative targets. The CLI was also run with the local compiler for oracle, call-flow, inheritance, and fixed-proxy fixtures.

## Current limits

This slice accepts one source file with no imports. Base contracts must be present in that file; missing bases stay unresolved. The graph represents source syntax, not EVM basic blocks or all runtime paths. `try` and inline assembly are recorded as unresolved, and their outgoing paths are omitted. Nested/multiple ternaries are also unresolved. A modifier with zero or multiple `_` placeholders, or a modifier definition absent from the supplied source, is left unspliced and explicitly uncertain. Value tracing unions branch and ternary origins conservatively; loops use one iteration and record uncertainty. Unsupported calls do not propagate an assumed return value. This is neither symbolic execution nor proof that every reported path is feasible. The graph does not model exception paths of arbitrary calls or arithmetic. It does not resolve deployment-supplied or mutable proxy targets, and a source-level relation is not independent verification of deployed bytecode. Function-name classification may differ from economic behavior; such classifications are hypotheses for later analysis. AST/source matching checks offsets and function names, not a cryptographic source hash. Bytecode recovery, detectors, LLM calls, and Foundry validation remain future stages.

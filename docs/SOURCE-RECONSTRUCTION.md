# Source reconstruction — M2 in progress

The Rust engine now accepts one explicitly supplied Solidity file, invokes a local `solc --standard-json`, and fills `EconomicFunction` records from the compiler AST. Run it with a `solc` executable installed locally:

```sh
cargo run -p security-engine -- tests/fixtures/VaultWithOracle.sol /path/to/solc
```

The command prints structured JSON IR. The library also exposes `reconstruct_source_file` and `reconstruct_from_ast_json` for callers that already have compiler output.

## Extracted now

- Named vault operations, previews, conversions and oracle price functions, classified from their names with `Inferred` confidence.
- Direct storage reads/writes, including compound assignments and indexed mappings, linked to source byte spans.
- Internal calls to functions in the same contract, explicit contract/address external calls, modifiers, arithmetic expressions and branch conditions.
- Oracle-call candidates when a price method is invoked on an oracle/feed/aggregator typed or named receiver.
- `delegatecall` receiver as a tentative proxy implementation candidate; ambiguity is recorded in `unresolved`.
- Locally defined modifiers resolved by the compiler's declaration ID. Their direct storage access, calls, arithmetic, and `require`/`assert` conditions are retained in `AppliedModifier` with invocation and definition spans, and included in the function's dependency lists. Parameters are paired with invocation arguments using source spans. For one `_` per modifier, the control graph runs through modifiers in source order, through the function body, then through modifier postludes in reverse order. A function-body `return` continues through those postludes, as specified by the [Solidity documentation](https://docs.soliditylang.org/en/latest/contracts.html#function-modifiers).
- A structural source control graph with `entry`, `exit`, and AST statement/expression nodes. Edges distinguish sequential flow, true/false branches, loop back edges, and exits. Each edge carries a source span. The extractor handles `if`, `return`, `revert` statements, `require`/`assert` guards, one ternary expression per statement, `while`, `for`, `do while`, `break`, and `continue`. In a `for` loop, `continue` reaches the update before the condition; in `do while`, it reaches the condition. Nested loops keep their own break and continue destinations.

Tests use AST snapshots generated by solc 0.8.37 from five small fixtures. They verify source locations, vault accounting relations, internal calls, modifier effects and bindings, composed control edges including nested loops, and tentative proxy evidence. The command was also run against the local compiler for the modifier fixture.

## Current limits

This slice accepts one source file with no imports. The graph represents source syntax, not EVM basic blocks or all runtime paths. `try` and inline assembly are recorded as unresolved, and their outgoing paths are omitted. Nested/multiple ternaries are also unresolved. A modifier with zero or multiple `_` placeholders, or an inherited modifier without a local definition, is left unspliced and explicitly uncertain. Parameter bindings pair syntax; they do not yet prove value propagation through the modifier. Inherited state is not resolved. The graph does not model exception paths of arbitrary calls or arithmetic. It does not yet trace data across functions or establish the actual implementation behind a proxy. Function-name classification may differ from economic behavior; such classifications are hypotheses for later analysis. AST/source matching checks offsets and function names, not a cryptographic source hash. Bytecode recovery, detectors, LLM calls, and Foundry validation remain future stages.
